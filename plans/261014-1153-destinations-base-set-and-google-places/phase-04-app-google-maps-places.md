## Overview

Goal: every map in the app is a Google map in our light and dark looks; search, the place page and photos come from Google through our api; the trip day works without a connection from our own text with a handoff to Google Maps.

Done when: Android and iOS e2e builds show every map screen on Google in light and dark (design | device sheets, `ui-reviewed`); search → pick → add to plan works on staging; the place page shows Google hours, rating and photos with credit; the airplane-mode trip day flow passes on Android; `planning-map-perf.yaml` stays in budget; no Google field is persisted on the phone (test).

## Decisions in this phase

| Call | Why |
|---|---|
| `react-native-maps` (the Expo SDK 58 version), `provider={PROVIDER_GOOGLE}` on both platforms | Google's map rule on iOS too; `expo-maps` draws Apple Maps on iOS |
| Styling with `customMapStyle` JSON (light and dark, switched with `theme.scheme`), no cloud Map ID | Founder decision 3 named a Map ID; JSON styling carries the same colours and feature visibility, needs no console step, switches at runtime, and does not bill map loads (a Map ID bills the Dynamic Maps SKU after 10 k loads a month). A Map ID becomes a small browser step only if a style needs cloud-only features (T1 records whether any does) |
| MapLibre removed in the same native build; no dual SDK | Old builds keep working because phase 3 leaves old routes until phase 5 |
| The map key values do not count toward the native fingerprint | The keys live in EAS env and GitHub secrets; a missing key on one machine must not change the runtime version (the Firebase-file incident pattern, `docs/system-architecture.md:321`) |

## Rollback

Testers reinstall the previous build from TestFlight / Play internal testing; the server keeps every old route until phase 5. JS fixes ship as updates to the new runtime. The lane's PR can be reverted as a whole before phase 5.
